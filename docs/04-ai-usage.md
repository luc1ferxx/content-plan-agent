# 04 AI 使用说明

试卷要求如实记录 AI 使用范围、个人贡献与验证结果。本文由 Claude Code 根据开发对话起草。“候选人做了什么”一列只写对话记录能核实的事；记录里没有的内容放在文末的“候选人填写区”，由候选人提供。

## 使用范围（如实记录）

本仓库的代码、测试、合成数据、运行记录和文档初稿都由 **Claude Code（模型 Claude Opus 5.5）** 生成，评审由它编排的多智能体工作流完成。

运行时，Agent 的决策由 DeepSeek 模型做出（离线 Mock 模式除外）。这部分是产品功能，不属于开发辅助。

| 阶段 | AI 做了什么 | 候选人做了什么 |
|---|---|---|
| 理解题目 | 根据题目截图拆解验收点 | 提供项目题截图；启用多智能体工作流 |
| 方案设计 | 设计计划与步骤状态、成本模型、决策接口、幂等与续跑规则 | 采纳 AI 的设计，未做修改。本人做的决定：要求优先保证进度；提供 DeepSeek Key，让 Agent 用真实模型决策（Key 只放在被 gitignore 的 `.env` 中，未提交）；选择改交本题 |
| 代码与测试 | 生成 `src/`、`tests/`、`data/`、`examples/inputs/` | 亲手做了一处修改，见文末“候选人填写区” |
| 真实模型运行 | 用 `deepseek-v4-pro`、`deepseek-flash` 跑全部场景，分析记录 | 提供 Key，授权调用 |
| 评审与修复 | 编排多视角的对抗性评审，按发现修改代码、补测试 | 未参与 |
| 文档 | 生成 README 和 `docs/` | 提供文末“候选人填写区”和“学习收获”的内容，由 AI 整理成文字 |
| 交付核对 | 最初只根据题目截图判断“可以直接提交”，这个判断是错的 | 追问“我希望有我参与的部分（题目要求写出来吗？）”。AI 因此才去核对试卷说明，发现遗漏了统一交付规范，随后整体返工 |

## AI 生成后做过的验证

**评审者可以复现（不需要 Key）：**

1. **测试**：`python -m unittest discover -s tests -v`，58 项，在 Python 3.12.1 和 3.10.0 上全部通过，输出见 [test-results.txt](../examples/test-results.txt)。
2. **离线 Mock**：`python -m src.run_examples` 跑全部 14 个场景。Mock 是确定性的，`tests/test_records.py` 会重跑并与提交的记录逐字段比对。
3. **随机决策测试**：`tests/test_fuzz.py` 用固定种子跑 600 个随机请求，决策模块随机选动作或返回垃圾输出，检查预算、依赖和状态的不变量。

**需要 Key，而且模型的结果每次可能不同：**

4. **真实模型**：`deepseek-v4-pro`、`deepseek-flash` 各跑全部 14 个场景，记录在 `examples/real-*`。`tests/test_records.py` 逐份检查这些记录：预算、依赖、状态都对得上；标注的决策来源是模型，没有回退 Mock；每次决策都带接口返回的响应 ID；故障场景确实碰到了注入的故障。这些检查核对的是记录本身，不能独立证明记录没有被改动。

## 过程记录（评审者无法从仓库复现）

下面的对抗性评审由 AI 编排的审查智能体完成，审查脚本没有放进仓库。

**第一轮（开发初版）**：3 个审查智能体分别从评分标准、状态与记账、健壮性三个角度审查，要求只报告能复现的问题，共 16 条，去重后 13 条：

- **已修复 11 条**，例如：缺口说明在预算和时间同时超限时选错方案；估算占用的 1 分钟把唯一可行的方案挤出截止时间；密钥含换行时会写进输出和状态文件。控制台编码在 PowerShell 中手工验证，其余用回归测试覆盖。
- **部分修复 1 条**：进程崩溃后的状态一致性（见 [03 评估](03-evaluation.md)「失败与限制」）。
- **未修复 1 条**：并发重复提交，列为已知限制。

**第二轮（重写决策循环之后）**：3 个审查智能体分别从试卷规范、文档事实核查、决策循环攻击三个角度审查，共 27 条，去重后 22 条：

- **代码问题 10 条**，已修复并由回归测试或随机决策测试覆盖。例如：模型把 `plan:P1` 填进 `action` 时被当成停止执行；模型全部失败时整次运行仍标为真实模型；主动放弃的可行方案之后用不了，却报告“没有可行方案”；“重新提交即可续跑”在来不及时无法兑现。其中保存后崩溃的问题只修了一部分，残留的窗口写进了已知限制。
- **文档问题 11 条**，已更正。例如：把“别无选择时的停止”写成模型的选择；把只核对标注的测试写成“确实来自模型”。
- **提交问题 1 条**：GitHub 仓库和 commit SHA，在提交时完成。

两轮评审里的批量运行（第一轮约 9.8 万次，第二轮约 12.6 万次）都没有发现超预算、依赖先后或状态不一致的问题。这些运行都发生在相应的修复之前；当前代码由 `tests/test_fuzz.py` 和运行记录自检覆盖。

## AI 自查发现并修正的问题

- **第一版不是模型驱动的。** 只在出问题时才问模型，正常路径是串行调用，不满足试卷的决策要求。重写循环后，每次工具调用都由一次决策选中。
- **发给模型的状态有误。** 当前方案被标成不可行，模型因此主动降级，故障场景没有碰到注入的故障。详见 [03 评估](03-evaluation.md)。
- **模型输出多余内容被误判为服务故障。** 详见 [03 评估](03-evaluation.md)。
- **预估多算一次估算**，导致模型看到的完成时间比实际晚 1 分钟。

## 未验证 / 不能由 AI 证明的部分

- 真实模型的稳定性只覆盖最终代码的一轮全量（两个模型各一次），没有做统计意义上的多次评测。
- 没有用真实的素材库和脚本服务验证过，工具都是合成的。
- 本文不能证明候选人的个人贡献，个人贡献以下面的填写内容和面试问答为准。

## 候选人填写区

以下内容由候选人提供，文字由 AI 整理，经候选人确认。

- 实际用时：约 3.5 小时。这是两段开发对话的总时长（2026-10-29 11:00–12:36，2026-10-31 约 10:50–12:45），包含等待模型和审查运行的时间，期间同时在做其他题目。
- 我亲自做的一处具体修改：AI 初版在截止时间早于开始时间时，仍会调用模型和估算工具，最后提示“时间还差 94 分钟”，这个提示有误导性。我在 `src/request.py` 的输入校验里加了判断：截止时间不晚于开始时间时直接报输入错误（退出码 2）；并在 `tests/test_acceptance.py` 的 `test_format_errors_raise` 里加了对应用例。这个问题和改法由 AI 提出，代码和测试由我亲手修改，并自己运行确认。
- 我自己验证过的结论：运行过 `python -m unittest discover -s tests`（58 项通过）和命令行示例（参考实例改选 P2、费用合计 8；截止时间早于开始时间时报输入错误）；看过 `examples/` 下的运行记录，读过核心代码。
- 我不同意或没采纳的 AI 建议：AI 建议提交题 1（当时题 1 的仓库和材料已经完整），我选择改交本题。
