# 02 方案：调用流程、动态决策与技术取舍

## 整体结构

```text
请求 → request.py 校验（缺输入直接返回 needs_input）
          │
          ▼
       agent.py 执行器  ◄──── 每一步询问 ────►  决策模块
       ├ 任务计划、步骤状态                     ├ llm.py：DeepSeek（真实模型）
       ├ 账本、模拟时钟                         └ policy.py：MockPolicy（离线 Mock）
       ├ 允许动作的计算与决策校验
       └ 运行状态落盘（state.py）
          │
          ▼
       tools.py 四个工具  ──► catalog.py 费用表、方案模板、素材
                          └─► state.py 方案库（幂等写入）
```

没有用 Agent 框架，循环是原生实现的。题目的核心是状态和重规划，这部分逻辑要显式写出来才能核对，框架帮不上什么。

## 调用流程

“估算 → 检索 → 脚本 → 保存”是预设的执行骨架，每一步由决策模块选择动作：

```text
决策：plan（选方案）
  └► estimate_cost ──观察──► 决策：call_tool / switch_option / stop
       └► search_materials ──观察──► 决策：call_tool / retry / switch_option / stop
            └► generate_script ──观察──► 决策：call_tool / retry / switch_option / stop
                 └► save_plan ──观察──► 全部步骤满足：执行器判定 completed
```

`stop` 只在没有其他可行动作时才允许；改选方案后先回到 `estimate_cost`，重新估算。

参考实例（预算 10）的实际过程：

1. 模型还不知道成本，选效果最好的 P1。
2. `estimate_cost` 返回预计合计 12，超过预算 10。
3. 模型观察到超预算，改选 P2，生成计划 v2。
4. 再次 `estimate_cost`，返回 8，通过。
5. 模型依次选择检索、生成脚本、保存，费用合计 8。

真实模型的完整记录见 [03 评估](03-evaluation.md)。

## 动态决策

### 动作

| 动作 | 含义 |
|---|---|
| `plan` | 选定方案，生成任务计划（开始或续跑时） |
| `call_tool` | 调用计划里的下一个工具 |
| `retry` | 重试刚失败的步骤 |
| `switch_option` | 改选替代方案，生成新版本计划并重新估算 |
| `stop` | 停止并说明缺口 |

### 一步决策的过程

1. 执行器把工具结果翻译成观察事件：`step_ready`（结果符合预期）、`estimate_rejected`（超预算或超时）、`tool_error`（工具错误）、`partial_result`（部分成功）、`guard_violation`（执行前校验不通过）。
2. 执行器算出当前允许的动作（`src/policy.py` 的 `allowed_actions`）：
   - 只有下一个依赖已满足的工具可以调用；
   - `retry` 要求错误可重试、没超过尝试次数，并且重试后仍在预算和截止时间内；
   - `switch_option` 只能选没被否决、依赖的工具可用、素材够用、预计在预算和截止时间内的方案；
   - 没有其他可选动作时，才允许 `stop`。
3. 决策模块选一个动作，并给出简要依据。
4. 执行器校验决策。不合法或无法解析就退回给模型重选一次，仍不合法时这一次决策改用 Mock；模型服务故障（超时、网络、鉴权）时，本轮剩余的决策都走 Mock。两种情况都会在决策记录里写明原因，整次运行的 `mode` 标为 `real_model_with_mock_fallback` 并带上边界说明。

模型决定走哪条路，执行器保证无论怎么走都不会越界。比如模型不能选已被否决的方案，也不能在有可行动作时放弃。所以 `stop` 严格说是“别无选择时的结束”：这时模型的作用是说明缺口。是否完成也由执行器判定，模型不能宣布完成。

### 成本信息的来源

首次规划时不把成本预估发给模型，它只看到方案的名称、优先级和素材要求，成本要通过 `estimate_cost` 观察到。这样模型的调整才是真的“看到工具结果后改变主意”。规划之后的每一步决策，都附带按费用表算好的候选方案预估，帮模型判断当前方案是否还可行、替代方案选哪个。

按费用表已经晚于截止时间的方案，首次规划时不提供：估算本身要占 1 分钟模拟时间，可能把唯一可行的方案也挤出截止时间。全部方案都来不及时，只提供优先级最高的一个，用于估算并返回缺口。超预算的方案则保留，因为估算不收费。

### 终止

单轮执行内，被否决的方案和不可用的工具只增不减；同一步骤最多尝试 2 次。主动放弃的方案在正常推进时不能换回来，当前方案出问题后可以再选。此外还有两道硬上限：单轮工具调用 15 次、决策 30 次。达到上限时返回 `incomplete`，`stop_code` 为 `TOOL_CALL_LIMIT` 或 `MODEL_TURN_LIMIT`，所以循环一定会结束。

未完成时的 `stop_code` 还有：`NO_FEASIBLE_OPTION`（没有方案能满足预算和截止时间）、`TOOL_UNAVAILABLE`（依赖的工具不可用）、`NO_MATERIAL`（素材库没有相关素材）。缺少必要输入时是 `MISSING_INPUT`。

## 成本与时间模型

- 费用全部查 `data/tools.json`，代码里不写死数字：P1 = 0 + 2 + 10 + 0 = 12，P2 = 8，P3 = 5；耗时 133、73、33 分钟。
- 计费规则：成功或部分成功收 `fee`，失败收 `fee_on_failure`（AI 分镜 2、标准脚本 1、其余 0）。每次调用的耗时（包括失败的）都计入模拟时钟。
- 费用合计 = 账本之和。`estimate_cost` 和执行器校验共用 `Catalog.project` 这一套算法。

## 状态设计

- **计划**：带版本号的步骤列表。依赖关系是：检索 ← 估算；脚本 ← 检索 + 估算；保存 ← 脚本 + 估算。估算结论为“通过”才算满足依赖。
- **步骤状态**：`pending`、`running`、`succeeded`、`partial`、`failed`、`blocked`（运行停止未执行）、`superseded`（被新计划替换未执行）。
- **重规划**：生成新版本。没执行的旧步骤标为 `superseded`；已成功的步骤（或部分成功但够新方案用的步骤）被新计划直接引用，不重新调用、不重新计费；失败步骤保持 `failed`。
- **持久化**：每次状态变化都原子写入 `.runtime/runs/<request_key>.json`，调用工具前先写“执行中”。

## 幂等与续跑

- **幂等键** = hash(主题, 预算, 截止时间)，不含开始时间、request_id、上限和故障注入开关。
- **已完成的请求**再次提交：直接返回，`repeat=true`，零调用、零决策、零费用。
- **未完成的请求**再次提交：续跑。保留全部历史和成功步骤，只重新允许导致上次停止的失败步骤所用的工具；其他已判定不可用的工具不自动重试，免得每次重复提交都把整条失败链重跑一遍。然后重建计划、重新估算剩余成本，只执行还缺的步骤。
- **方案库**按请求幂等：内容相同不重复写，内容变化时版本号 +1，同一请求始终只有一份方案。
- **进程中断**：步骤停在“执行中”时，续跑会补一条 `INTERRUPTED` 调用记录（不计费、不计时），按失败处理后重做。保存结果已落盘、只差收尾时，续跑直接收尾，不重复保存。
- **是否提示续跑**：只有续跑后还有方案能在预算和截止时间内完成，才提示“重新提交即可续跑”；否则明确说明重复提交不会改变结果。

## 技术取舍

| 决定 | 原因 | 代价 |
|---|---|---|
| 保留预设骨架，模型只选动作，不开放任意调用工具 | 题目的交付物就是“任务计划和步骤状态”，依赖关系要能核对；试卷也允许用预设流程做骨架 | 模型的自由度小于完全自由的工具调用，工具参数由执行器按计划填入 |
| 允许动作由执行器算好再给模型 | 预算、依赖这些硬约束不能依赖提示词；模型也更不容易选错 | 模型看到的是筛选后的选项 |
| 模型调用无状态（每步发送完整状态） | 所有上下文都在持久化状态里，续跑不需要恢复对话 | 每步都发一遍状态，token 略多 |
| 用 JSON 模式，不用函数调用 | 只需要一个结构化决策，标准库就能实现，无第三方依赖 | 输出要自己解析和校验 |
| 工具成本由模拟费用表决定，不接真实计费 | 试卷允许本地函数和 Mock；数字确定，评审可以手工核算 | 不反映真实服务的费用波动 |
| 失败调用按 `fee_on_failure` 计费 | 让失败有真实代价，决策时必须考虑沉没成本和重试是否划算 | 计费规则多一个字段 |
| 幂等键包含预算和截止时间 | 约束变了，方案就可能不同，按新请求处理最不容易出错 | 追加预算后不能沿用已有结果 |
| 文件存储加原子替换 | CLI 单进程够用，零依赖，状态文件能直接打开检查 | 没有并发控制 |
