# 05 复盘：最难的问题、收获与下一步

## 最难的问题（项目层面）

1. **“模型决策”和“程序兜底”的边界放在哪。**
   题目要求模型调整计划，固定分支不算完成决策；但预算、依赖、“失败不能记为成功”又不能交给提示词去保证。
   最终做法：执行器先算出当前允许的动作，模型在里面选；账本、时钟、状态只由执行器写。这样模型选哪条路都不会越界。

2. **第一版其实不是模型驱动的。**
   第一版只在超预算、工具失败这些节点才问模型，正常路径完全不经过模型，看起来就是串行调用。核对试卷说明后才发现这不满足决策要求。
   重写循环后，模型在每一步都会看到上一步的结果再选下一步，离线 Mock 走同一条循环并在每份输出里标注边界。

3. **重规划之后，步骤状态怎么保持真实。**
   改选方案时，同一个“素材检索”可能在旧计划里部分成功，在新计划里又够用。如果为了好看把它改成“成功”，就和实际调用对不上。
   最终做法：步骤状态永远反映它自己的调用结果，新计划只是引用它，并写明“部分成功（2 条），满足 P2 需要的 2 条，复用”。
   测试和运行记录自检都会核对“状态 = 最后一次调用结果、尝试次数 = 调用记录数”。

4. **模型什么时候该知道成本。**
   如果规划时就把各方案的费用预估发给模型，它会直接选便宜的方案，看不到“观察工具结果后调整”。
   最终做法：首次规划不给成本，成本由 `estimate_cost` 返回；规划之后的每一步才附带候选方案的预估，帮它判断和选择。
   这里还有一个反直觉的边界：估算本身占 1 分钟模拟时间，先估算一个明显来不及的方案，可能把唯一可行的方案也挤出截止时间。所以已知来不及的方案在规划时不提供（全部都来不及时，只提供优先级最高的一个，用于估算并返回缺口）。

5. **续跑该放开多少。**
   最初续跑时清空全部“工具不可用”标记，结果故障没恢复时，每次重复提交都把整条失败链重跑一遍，费用和时间不断累积。
   现在只重新允许导致上次停止的那一步，其他已判定不可用的工具不自动重试。代价是工具恢复后不会自动回到效果最好的方案，要用 `--reset` 重来。

6. **Mock 全部通过，不代表真实模型没问题。**
   第一次全量跑真实模型时，`deepseek-flash` 在估算通过后主动降级，故障场景根本没碰到故障。原因是发给模型的状态把当前方案标成了“不可行”，这个错误对 Mock 没有任何影响。
   另一个问题是模型偶尔在 JSON 后面多输出内容，解析失败被误判成服务故障。
   从这里得到的做法：运行记录也要有测试，不只检查“记录没违规”，还要检查“这份记录确实走到了它声称覆盖的场景”。

7. **最初漏看了统一交付规范。**
   开发时只对照了题目本身的要求，没有核对试卷总说明，第一版的目录、运行记录和决策循环都不符合规范，后来整体返工。
   这次的教训是：动手前先确认全部约束的来源，而不只是眼前这一道题。

## 学习收获

以下要点由候选人选定，文字由 AI 整理。

1. **真实模型能发现 Mock 发现不了的问题。** 这次 Mock 和测试全部通过，真实模型一跑才暴露出状态标错和输出解析失败。
2. **模型决策和程序兜底要分开。** 模型负责选动作，预算、依赖和状态这些底线由程序保证，这样模型怎么选都不会越界。
3. **动手前要先看全部规则。** 这次只看了题目，没看试卷总说明，结果目录、运行记录和决策循环都要返工。
4. **状态要如实记录。** 重规划时，失败和部分成功都不能为了好看而改写；运行记录本身也要能被检查。

## 下一步

1. **评测集**：把场景扩展到几十个合成请求，每个模型重复多次，统计方案选择正确率、改选次数和平均决策次数。
2. **模型的决策空间**：现在模型只选动作，工具参数由执行器填入。下一步可以让模型决定检索词，素材不够时先补搜，再决定是否降级方案。
3. **预算追加后的续跑**：现在预算或截止时间变了就算新请求，已有结果带不过去。可以把幂等键改为只看主题，变更预算时沿用已成功的步骤。
4. **并发控制**：给同一请求加运行锁，第二个并发提交直接返回“运行中”。
5. **保存的崩溃恢复**：进程恰好在保存工具写入方案后、调用结果落盘前中断时，续跑会再保存一次。可以先查方案库，确认已写入就不再重复保存。
6. **真实工具**：把素材检索和脚本生成换成真实服务，执行器和决策逻辑不用改。
